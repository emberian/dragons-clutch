## 2. Decisions made here that the ruling left open (BINDING for the successor lane)

1. **Admission by moved-ness, no builder knob.** The route decides
   per-binding: successor record digest ≠ V1's pinned id ⇒ MOVED ⇒
   `FirstAdmission` (full-ELF hash, mandatory — no prior admission
   exists); equal ⇒ UNMOVED ⇒ `AlreadyPinned` (sound: V1's first admission
   hashed those exact bytes; the pin is re-proven against the live
   observation). §7's CU note is thereby structural, not optional.
2. **Both-bindings-unmoved is refused** (`InfrastructureNotForward`): it
   selects nothing new and would burn the domain's one vacancy — the
   lineage self-succession refusal (its conjunct 3), carried over.
3. **Conjunct 2 does NOT re-authenticate V1's deployments.** Presence =
   exact PDA, Core-owned, exact 144 width, non-executable, rent-exempt,
   hostile-decodes. Re-running V1's pinned read would refuse
   `ReleaseSuperseded` post-upgrade — the exact situation the ceremony
   exists for. Deliberate; documented at
   `authenticate_predecessor_profile`.
4. **The predecessor record is content-pinned, never observed.** For a
   moved binding the predecessor's `ArtifactReleaseV1` record account is
   presented; its sha256 must equal V1's pinned artifact id (a different
   record has a different digest), then `authenticate_finalized_record` +
   decode + program match + `require_slot_pinned_release_v1`. Its
   deployment is NOT observed — it is gone; the record's slot and bound
   authority were proven truthful at V1's first admission.
5. **An `Immutable` predecessor refuses a moved claim** under
   `InfrastructureConsentMissing` (no authority to consent; its bytes
   cannot have moved) — same shape as lineage's
   `ReleaseLineageAuthorityMissing` contradiction arm.
6. **Magics/versions:** profile `DCLTINF2`, instruction `DCLTIIN2`,
   schema version 2, artifact profile 1 (unchanged — the artifact-record
   format did not move). Reserved tail 16 bytes (nothing can ever be
   written into a write-once account later; the tail exists so a hostile
   decode has a canonical-zero span, and it is enforced non-zero-refusing).

## 8. The deploy order the cut inherits (ruling §6, concretized)

Steps 3–5 are ONE scripted batch; the refusal window between them is
structural (first admission can only hash deployed bytes).

1. Pre-upgrade sweep (gate 6 first half): settle `fee_owed`, drain
   markets 21/22, archive life tables; any market needing PROVIDER

2. Publish finalized `ArtifactReleaseV1` records for the new Registry
   deployment (Rent stays unmoved per ruling §9.2 — its V2 binding is
   byte-identical, `AlreadyPinned` at the ceremony, System in its
   consent slots).
3. Upgrade the programs: the five-role set + the Registry (`d6e43b11`'s
   ELF) **+ resolution-proof and Core built WITH the V2-only reads**
   (Packet A must land before the cut ships). From this instant routes

   predecessor-registry-authority sign (same key on devnet). Routes 1–6
   un-refuse via Core's V2 read; 7–8 via resolution-proof's.

   8→9. Under this ruling Resolution flips to MOVED in 8→9 (its consent
   slot becomes authority-signed); Custody is the expected sole unmoved
