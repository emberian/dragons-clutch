# dClutch Lean semantics

`DClutchSemantics` is the one place a dClutch protocol fact is stated so that
both a Rust crate and the browser can be printed from it.  The package has no
dependency on the Rust implementation or on the neighbouring research
repositories; Rust is a differential oracle, not a source of definitions.

## What is here

- **ABI modules** (`*Abi.lean`, and the `*V1`/`*V2`/`*V3` record modules):
  one per persisted or signed record.  Each states the record as `AbiSchema`
  data -- field names and wire kinds; `specialize` is the only owner of
  offsets -- together with its magics, seed domains and reserved spans, and
  proves the width, name uniqueness, disjointness and coverage (`tiles`) that
  pin them.  A schema edit that would move a live account boundary fails here
  before it can reach either backend.
- **Transition systems** beside them (`Direct`, `DirectLifecycle`,
  `SourceResolution`, `MarketCore`, `Series`, `GeneralClearing`,
  `DealerLiquidity`, `StructuredV2`, `EconomicKernel`, ...): the pure
  semantics, their conservation and refusal theorems, and executable
  `*Examples` regression modules that pin the theorems to concrete numbers.
- **Mechanism modules** (`JointClearingV1`, `ScoringRuleV1`,
  `EnsembleResolutionV1`, `FounderBondV1`, `ConditionalMarketV1`): the design
  layer for the next cohorts.  Two `sorry`s in `ScoringRuleV1` are stated with
  their reasons.
- **Printers**: `RustEmit` and `TsEmit` are the two backends.  `RustEmit`
  imports nothing and `Codec` imports it, which is what makes it reachable
  from every guard.
- **Emitters** (`Emit*.lean` at the package root): one per record, each a
  script run as `lake env lean --run Emit<Record>.lean [target]`.  A record
  with both a crate and a browser module has one emitter with `rust` (the
  default) and `ts` targets; `EmitRegisteredDirect.lean` prints
  `lifecycle`, `controller` or `ts`.  The emitters are not library modules and
  the lakefile declares no executables: every guard builds the ABI module it
  names and runs the emitter as a script.
- **vectors/**: the four Lean-emitted fixtures Rust and TypeScript tests
  consume byte-for-byte; `vectors/MANIFEST.md` names each consumer.

`DClutchSemantics.lean` is the alphabetical list of every module and is
regenerated by the one-liner at its top.  The lakefile's glob, not that list,
decides what `lake build` compiles.

## How a record is owned

1. State the layout once as `AbiSchema` data in `DClutchSemantics/<Record>.lean`
   with the width, uniqueness, disjointness and coverage theorems.
2. Write `Emit<Record>.lean` printing every target the record has through
   `RustEmit` / `TsEmit`.
3. Point the crate at the generated module and add its guard
   (`check-generated.sh`, or a `tests/*_generator_fresh.rs` that re-runs the
   emitter, normalises with `rustfmt --edition 2024`, and byte-compares); for
   a browser or SDK module add `abi:<record>` and `abi:<record>:verify`
   scripts calling `scripts/lean-emit.mjs ... Emit<Record>.lean <file> [--check] ts`.
4. Delete whatever the crate or the browser was hand-stating.

`tools/emission-guard/COVERAGE.md` is the census of which generated file has
which guard; `tools/ci/run.sh emission` runs every guard for real.

## Building

`lake build DClutchSemantics` builds the library (toolchain in
`lean-toolchain`).  Regenerate one emission with
`lake build DClutchSemantics.<Record> && lake env lean --run Emit<Record>.lean [target]`.

`TRUST.md` states what is machine-checked and what remains an unverified
adapter boundary.
