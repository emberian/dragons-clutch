# Decision 0006: a hot action selects its family by proved selection, and the Hot executor never branches on it

Status: accepted on 2026-08-27 as the resolution of the dispatch question W2h
scoped and declined ("Item 3 (TA-GEN's General wiring): NOT a one-line call
site"). This is an authority and dispatch decision. It is not release evidence,
it is not a claim that any General hot action executes today, and it does not
by itself delete anything — the convergence it names has an owner and a cost,
both recorded in §5.

## Context

`programs/dclutch-trading-sbf/src/general/hot_slice.rs::process_general_hot_slice_v2`
landed complete and tested with no caller. Three lanes in a row described the
remaining work as "one call in `hot_v3`". W2h measured that it is not, and
named the four decisions the call site would need: a family selector, an
account-suffix contract, a writability decision, and adversarial tests. This
record answers the first two, rules on the third, and finds that the fourth
question is asked of the wrong object.

## 1. The selector already exists, it is two-level, and neither level is a guess

**Level 1 — the family.** The account at `HOT_ROOT_ACCOUNT_V3` (index 1) is a
composite `CapabilityRootHeaderV1(232) || <family tail>`. Its immutable header
carries a `CapabilityExecutionSelectionV1`, and the account's own address is
`find_program_address` over exactly that selection
(`crates/dclutch-capability-program-contract/src/lib.rs:563`):

```text
[CAPABILITY_ROOT_PDA_DOMAIN_V1, market, generation, manifest,
 entry_index, kind, capability_release, config]
```

`kind` is a seed. An account at that address cannot carry a selection naming a
different kind than the one it was derived from. `hot_v3.rs` then joins that
selection to two independently authenticated records:

```text
hot_v3.rs:1610  authenticate_root_boxed_v3        header + derived address
hot_v3.rs:1631  authenticate_manifest_entry_boxed_v3   Market manifest entry
hot_v3.rs:1698  authenticate_descriptor_root_selection
                  -> CapabilityProgramV4::validate_selection (v4.rs:189)
                       descriptor.kind    == selection.kind == entry.kind_id
                       entry.release_id   == selection.capability_release
                       entry.config_id    == selection.config
                       descriptor.root_schema      == entry.child_schema_id
                       descriptor.derivation_policy == entry.child_derivation_id
                  -> descriptor.root_account_bytes() == context.root_account_bytes()
```

So by the time any family-owned code could run, "this is a General capability"
is a **proved conjunction of a PDA derivation, a Market manifest entry, and a
sealed descriptor** — not an inference from how many accounts arrived or what
shape they have.

**Level 2 — the action.** `CapabilityProgramSetV2::select_entry(family_request)`
(`set_v2.rs:305`) reads a selector at the *set-declared* `selector_offset` /
`selector_width` and returns the descriptor reference for it. General declares
byte 10 of its canonical 64-byte request
(`GENERAL_CONTROLLER_ACTION_SELECTOR_OFFSET_V3`, matching
`CONTROLLER_REQUEST_ACTION_OFFSET_V2`). The selected `(schema, program,
selector)` triple is then a **seed of the capability seal**
(`authenticate_capability_seal_v3`, `hot_v3.rs:1673`), so the action is sealed
rather than switched on.

## 2. The account-suffix contract is the AccountProfile artifact

There is no per-family index table to write, because the executor does not have
one for any family:

```text
hot_v3.rs:2067  expand_runtime_accounts_v3(
                    account_profile, product_outcome_count, &widths,
                    [root, config_raw, product_raw, portfolio_raw, linked_basis_raw],
                    accounts[runtime_start..])
```

A hot frame is `HOT_FIXED_ACCOUNT_COUNT_V3` (39) fixed accounts, then six or
eight authenticated strategy extras, then — for admitted AOT — the
release-pinned caller authorities, then the runtime accounts that the
**selected AccountProfile** expands. General's AccountProfile is generated by
`crates/dclutch-general-adapter-contract/src/account_rules_v3.rs::general_account_profile_rule_v3`,
and the operator that builds the instruction says the same thing in its own
words (`crates/dclutch-operator/src/general_hot_v3.rs:413`):

> The action-specific account width and privileges come only from the selected
> AccountProfile; this operator carries no parallel per-action account table.

A hand-written `GENERAL_CONSIDER_ACCOUNT_COUNT = 12` in the executor would be a
second authority for a fact the artifact already owns.

## 3. The ruling: `hot_v3.rs` gets no General branch

`outer.rs:5` states the invariant for the activation boundary — "It does not
dispatch on a capability kind" — and `hot_v3.rs` holds it too: one
case-insensitive `general` match in 9,925 lines, and it is a PDA seed string.
The `series-family` / `dealer-family` `cfg`s are link-time gates on child-route
composition, not runtime family dispatch.

**A General hot action does not need a dispatch point, a selector, or an
account-suffix contract to be added.** It needs a founded General capability
whose descriptor closure the executor authenticates — and that closure already
exists, is built for these exact coordinates
(`artifacts_v3.rs` imports `HOT_RUNTIME_{ROOT,CONFIG,PRODUCT,PORTFOLIO,LINKED_BASIS}_COORDINATE_V3`
directly), and has been executed at both runtime widths against a real ELF
(`docs/evidence/GENERAL_ACCELERATOR_CAMPAIGN_2026_08_27.md`).

## 4. The writable-root ruling

TA-GEN left open whether `process_general_hot_slice_v2` should require the root
account writable. **Writable, and the question is already settled twice over on
the data-defined path, more precisely than a family-side check can settle it:**

- General's own AccountProfile declares the root writable, per action, at
  coordinate 0, with `no_effects()`
  (`account_rules_v3.rs:216-229`, exact width `CAPABILITY_ROOT_HEADER_BYTES_V1
  + GENERAL_ROOT_BYTES_V2` = 360).
- `hot_v3.rs:7286 require_root_write_is_state_only` refuses any resolved write
  whose representative coordinate is 0 and whose offset is below
  `CAPABILITY_ROOT_HEADER_BYTES_V1`. The immutable header is fenced by the
  executor, not by family courtesy.

Writable is the fail-closed choice: a family that may retire its own tail needs
the privilege, and the header it must not touch is protected by a conjunct the
family cannot skip. The narrower point stands against the *slice*, though — a
blanket `!root_account.is_writable => refuse` demands the privilege on
`Consider`, `Freeze` and `InitializeSettlement`, none of which write the root,
while the AccountProfile can and does state it per action.

## 5. What this record found on the way: General has two generations

The slice cannot be wired because it belongs to the superseded one.

| | V1/V2 generation | V3 generation |
|---|---|---|
| request | `ControllerRequestV1`, `[u64; MAX_OUTCOMES]` | `successor_request_v2::ControllerRequestV2`, 64 B, runtime width |
| config | `GeneralConfigV2` (232 B, carries `outcome_count`) | `v3::GeneralConfigV3` |
| outcome bound | `MAX_OUTCOMES = 16`, `MAX_OUTCOMES_V2 = 16` | Product owns the width |
| semantics | `general-adapter-contract::{CandidateVerifierV1, consider_verified_input, freeze_selection, initialize_settlement}` | `…::{runtime_selection, runtime_settlement, runtime_verify, runtime_width}` |
| activation | `root.rs::activate_general_owned_v2` | `root_v3.rs::activate_general_owned_v3` |
| Trading adapter | `programs/dclutch-trading-sbf/src/general/{activation,hot_controller,route,settlement,controller,hot_slice}.rs` | none — the descriptor closure *is* the adapter |
| operator | `dclutch-operator::general_physical` (12/6/9/28 frames, **non-ALT** v0) | `dclutch-operator::general_hot_v3` (AccountProfile-expanded, ALT-backed v0) |
| executable evidence | none | seven actions, N=1 and N=258, real ELF |

`root_v3.rs:3` says it plainly: "This successor path admits only
`GeneralConfigV3`." `successor_request_v2` is named for what it is. The V1/V2
generation is capped at sixteen outcomes by fixed-width arrays, so it cannot
express the width its own family's campaign measures, and its 12/6/9/28 suffix
is not a suffix of any hot frame.

Wiring `process_general_hot_slice_v2` would therefore install a second General
authority, capped at N ≤ 16, behind a hard-coded kind branch in a deliberately
family-neutral executor — three violations of `AGENTS.md` in one call. **It is
not written, and this record is the reason.**

Neither generation is *reachable* today; that is not the difference between
them. The difference is that the V3 generation needs artifacts and a founded
root, and the V1/V2 generation needs an executor change nobody should make.

## 6. Consequences

- `hot_v3.rs` is unchanged by this lane. Its family-neutrality is now a written
  decision rather than an accident of what has been implemented.
- The V1/V2 General generation in `programs/dclutch-trading-sbf/src/general/**`
  (≈ 165 KB across six files) and `dclutch-operator::general_physical`
  (1,573 lines) are superseded paths under `AGENTS.md`'s convergence rule.
  Deleting them is a named, owned act that this record does not perform: the
  V3 side still has **no activation adapter** (`activate_general_owned_v3` and
  `plan_general_activation_v3` have no caller outside their own tests), and
  `general/activation.rs` is the only in-tree General activation planner. Delete
  the V1/V2 hot path once a V3 activation adapter exists; do not delete
  `general/activation.rs` before then.
- `crates/dclutch-operator/src/general_hot_v3.rs::build_general_hot_instruction_v3`
  — the function that *is* the General account-suffix contract on the operator
  side — has zero callers and zero tests. That, not a missing dispatch point,
  is the next thing standing between General and an executed hot action.

## 7. The zombie refusal is on the wrong generation

TA-GEN closed the zombie case on the slice: a `Retiring` or `Retired`
`GeneralRootV2` refuses, decoded from a composite root whose immutable header
is byte-identical to the accepted one. That refusal is correct and it is on the
sixteen-outcome generation.

**The runtime-width generation has no such refusal, because it never reads the
root tail at all.** Traced end to end:

```text
hot_v3.rs:2787  authenticate_root_boxed_v3 decodes root_data[..232] only
dispatch.rs:258 TradingFamilyContextV1::authenticate — the header and the length
hot_v3.rs:1698  authenticate_descriptor_root_selection — widths and identities
account_rules_v3.rs:216  root coordinate 0: exact 360 bytes, no_effects()
joined_artifacts.rs      zero references to the root coordinate: no operation
                         projects the lifecycle byte into any register
root_v3.rs:25   GeneralRootV2::require_hot_context_v3 — requires Active,
                         and has no caller outside its own tests
```

The header proves identity and says nothing about whether the capability still
accepts work; `hash(root bytes) == envelope.root_prestate_digest()` in
`process_hot_execution_v3` is a caller-declared replay binding, not a
constraint on the lifecycle value. So a retired General capability would still
execute hot actions on the reachable path.

It is latent rather than live — no V3 activation adapter exists, so no such
root can be created yet — and it must not be allowed to stop being latent
quietly. The fix is data-defined and it is not cheap: a root-lifecycle scalar
changes `GENERAL_HOT_COMMON_SCALARS_V3`, which moves the bank width, the page
count, and every artifact digest in the family. Recorded as `U-003`(a) in
`docs/OMISSION_INDEX.md`. Substrate, said out loud: these artifacts are
TransitionVM programs and AccountProfiles — interpreted data authored in Rust
contract crates — not AIR, and there is no constraint system in the Trading hot
path.

## 8. What a General end-to-end hot action still needs

1. A V3 activation adapter, so a General capability root can exist.
2. The root-lifecycle refusal of §7.
3. A capability seal for the selected `(descriptor, action)` pair — its own
   outer, already implemented (`hot_v3::process_capability_seal_v1`).
4. `build_general_hot_instruction_v3` exercised against a real `GeneralHotStateV3`.
5. ~~The packet witness for the N=258 account sets~~ — landed
   (`docs/evidence/GENERAL_ALT_PACKET_WITNESS_2026_08_27.md`).
6. The Trading hot tail past phase 7 (W2i), which is not General's to move.
