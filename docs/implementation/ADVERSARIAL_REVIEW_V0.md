# Dragon's Clutch adversarial integration review V0

Status: **STOP for integration, release, formal-verification, or chain-readiness
claims.** The current artifacts are useful offline falsifiers, but the vertical
model, adapter, layout, collateral policy, and formal shadows are not yet one
authenticated persistent protocol relation. Several cross-layer identities,
liveness policies, and conservation joins remain inconsistent or unimplemented.

Review date: 2026-08-18. This was an offline, read-only review of the untracked
worktree. It used no RPC, validator, wallet, key, signature, deployment, network
write, or financial action. This report is the only project source/document file
edited by the review; ignored local build output was generated by the gates.

## 1. Evidence and severity convention

- **P0 / STOP**: a confirmed defect that can authorize the wrong economic
  transition, repeat a transition beyond its allowance, settle before immutable
  terms permit it, or materially misstate verification/release status.
- **P1 / REDESIGN**: a confirmed semantic or integration mismatch that prevents
  the present components from composing into the documented protocol.
- **P2 / GATE**: a missing adversarial, operational, privacy, upgrade, or evidence
  closure that must be resolved before promotion but is not itself an observed
  invalid transition in the current deliberately offline scope.
- **Design question**: the repository has not selected one policy. It is not
  called a defect unless executable surfaces already imply incompatible answers.

deliberate refusals, liveness/design decisions, and missing evidence.

## 2. P0 regressions found and repaired during review

### Repaired during review: batch ineligible-fill acceptance

**Prior class:** P0 authorization and semantic integrity. **Current result:**
fixed and reproduced; retain as a permanent regression gate.

The first reviewed revision let `FixedBook::side_total` exclude a buy whose
`limit_tick` was below the clearing tick while `validate_fills` never required an
ineligible fill to be zero.

Executed counterexample on the public API:

```text
grid = [10, 20, 30]
order 1 = buy,  limit_tick 2, quantity 10
order 2 = buy,  limit_tick 0, quantity 10
order 3 = sell, limit_tick 2, quantity 10
chosen clearing_tick = 2
forged fills = [0, 10, 10]
FixedBook::verify(forged) = Ok(...)       # first reviewed revision
```

During this review, the implementation was repaired to recompute eligibility in
`validate_fills` and return `IneligibleFill`. The same executable counterexample
now returns:

```text
FixedBook::verify(forged) = Err(IneligibleFill)
```

The new regression test covers the buy direction. The stop remains closed only
while the inverse sell inequality and mutations of both comparisons are also
kept in the property/mutation suite.

**Regression gate:** every fill verifier computes the order's exact eligibility
at the candidate price and requires `fill == 0` when ineligible. Keep this exact
fixture and add mutations of both buy and sell inequalities before promotion.

### Repaired during review: canonical-allocation verification

**Prior class:** P0 authorization, fairness, and deterministic relation.
**Current result:** fixed and reproduced; the AON policy still needs a design
decision and exhaustive liveness analysis.

The first reviewed revision described and constructed a canonical pro-rata /
largest-remainder allocation in `propose`, while `verify` accepted any fill
vector satisfying loose bounds and side totals.

Executed counterexample:

```text
two eligible buys of 10 each; one eligible sell of 10
proposed buy fills = [5, 5]
forged buy fills   = [10, 0]
FixedBook::verify(forged) = Ok(...)       # first reviewed revision
```

The implementation was repaired during the review: `verify` now independently
recomputes both sides' canonical fill vector and requires exact array equality.
The same counterexample now returns `Err(CandidateMismatch)`, and the new
regression suite also rejects a manually supplied AON allocation that bypasses a
canonical-constructor refusal. Tests, strict Clippy, rustdoc warnings, and fmt
were rerun successfully.

The liveness/design question remains: minimum-fill/AON orders are counted at full
size for price/volume selection even when the canonical allocator cannot honor
them, so an otherwise matchable book may refuse as a whole. That behavior is now
consistent between construction and verification, but it is not yet shown to be
the desired market policy or resistant to intentional batch poisoning.

**Remaining gate:** the code now selects canonical allocation. Add exhaustive
tiny-book comparison including minimum fill, AON, dust, equal remainders, seed
changes, order fragmentation, both sides, and the explicit decision whether an
unfillable AON order may poison an otherwise feasible batch.

### Repaired during review: settlement domain, consideration, and paired orders

**Class:** replay, authorization, liveness/accounting ownership.

The first reviewed revision checked each requested quantity against the
candidate's fill but did not track the cumulative amount consumed. That exact
defect was repaired during this review with a per-candidate/per-order cumulative
ledger.

Executed counterexample using a candidate whose sell fill is 5:

```text
settle quantity 3 -> Ok
settle quantity 2 -> Ok
settle quantity 1 -> Ok                        # first reviewed revision
cumulative settled = 6 > candidate fill 5     # first reviewed revision
```

After repair, the same `3 + 2 + 1` sequence rejects the final unit. Clear replay
of an equal `Candidate` is also idempotent. Tests, strict Clippy, rustdoc
warnings, fmt, and the golden trace were rerun successfully.

The next revision repaired much of that identity and accounting seam. It added
an explicit `BatchDomain` containing market, book, epoch, policy, and order-set
identities; a `CandidateIdentity`; a ledger retaining the frozen orders and
clearing price; and a `SettlementReceipt` carrying one order index/ID, parties,
outcome, quantity, and exact consideration. Different book and epoch domains no
longer alias. The claim-only entry point refuses with `MissingConsideration`;
the new path rejects missing buyer cash and wrong price, moves buyer cash to the
seller, moves claims in the opposite direction, and checks joint cash/claim
conservation. These were substantive but incomplete repairs.

That intermediate revision still named and consumed only one side of the match.
It did not name the paired counterparty order, validate the stored order side,
or bind owners/outcomes. The independently tracked buy and sell fills could
therefore each authorize a complete asset/cash transfer even though they were
the two sides of one matched unit. An executed public-API counterexample showed:

```text
candidate.matched = 1
receipt(sell order 2, outcome 0, quantity 1, consideration 20) = Ok
receipt(buy  order 1, outcome 1, quantity 1, consideration 20) = Ok
buyer claims = [1, 1]
buyer cash = 0; seller cash = 40
```

Thus one unit of matched volume moved two claims and charged consideration
twice. Total cash and claims remain conserved; conservation alone does not prove
that the batch authorized those two transfers.

The final repair replaces that surface with `BoundOrder`, which freezes each
order's owner and outcome beside its side, and
`clear_batch_with_bindings`. A settlement receipt now names both buy and sell
indices and canonical IDs plus Candidate/domain, outcome, quantity, price, and
consideration. The accepted path validates opposite sides, distinct bound
owners, equal bound outcome, both fill ceilings, and exact clearing-price cash;
it mutates the claim and cash legs atomically and consumes both order ledgers.
Generic unbound books refuse settlement with `MissingPairBindings`. Reversed
pairs, wrong outcome/book/epoch/order/price, missing cash, and replay refuse.

The former double-settlement fixture now produces:

```text
paired trade = Ok
same paired trade again = Err(PairAlreadySettled)
matched = 1; buyer claims = [1,0]; buyer cash = 20; seller cash = 20
```

All seven tests, strict Clippy/rustdoc/fmt, and the golden trace pass. The observed
P0 is closed in this host model.

**Remaining P1 liveness/design gates:** a `(buy_index,sell_index)` pair is
one-shot even when its receipt quantity is smaller than both filled quantities.
The current test intentionally accepts quantity 3 against fills of 5 and then
returns `PairAlreadySettled` for the remaining 2, which can strand otherwise
settleable fill. Freeze either full-pair-only quantity, cumulative per-pair
remaining quantity, or unique match-slice receipts. Also, `order_set_id` is
caller-supplied rather than derived from order bytes, `BoundOrder` is not an
authenticated signature/reservation, and no persisted settlement-pot authority
exists. An eventual adapter must bind the exact canonical order-set commitment,
owner authorization, reservation/generation, fees/carry, and atomic receipt
state rather than treating these host values as authority.

### Repaired during review: vertical error atomicity

**Class:** error atomicity, hostile prestate, and retry safety.

The paired settlement method mutates Positions, cash, trace, and receipt ledgers
before its final `check_conservation()`. `VerticalModel` exposes its Market,
Positions, accounting, cash, and funded-total fields publicly, so an invalid
prestate is constructible through the public API. The final check can therefore
fail after the economic transition has already been committed in memory.

Executed counterexample:

```text
start with a valid bound candidate, seller claim 1, buyer cash 20
set public cash_funded = 21                 # aggregate is now invalid
settle paired quantity 1 for consideration 20
result = Err(InsufficientCash)
poststate buyer claims = [1,0]
poststate buyer cash = 0; seller cash = 20  # transfer survived the Err
```

This pattern was broader than settlement: split, materialize, dematerialize,
merge, funding, resolution, and redemption also mutate some combination of
kernel/accounting/trace state before their final cross-component conservation
check.

The final repair adds a clone/apply/check/commit transaction wrapper to every
publicly mutating `VerticalModel` transition. The public `Accounting`
reserve/pay/return methods and the internal fee mutator independently stage a
copy, validate it, and commit only on success. The exact corrupted
`cash_funded` settlement now returns `Err(InsufficientCash)` with the full
`VerticalModel` unchanged. The exact corrupted `Accounting` fixture now returns
`Err(LivenessConservation)` with reserved/paid/funding unchanged at `1/1/1`.
The seven-test suite and strict gates pass.

**Remaining boundary:** most host state fields are still public and therefore
directly mutable without invoking a transition. The repaired API refuses and
preserves such a hostile prestate, but the type itself is not an authority or a
valid-state capability. Treat those fields as host-inspection scaffolding. A
persisted adapter must decode/authenticate its prestate; a stronger host API
should expose read-only views or private fields. Retain exact state-equality
checks for every refusal and mutation-test the staging wrapper.

### Repaired during review: prefix resolution before maturity/sealing

**Prior class:** P0 resolution authority, liveness, and event integrity.
**Current host-model result:** fixed and reproduced; authenticated source/window
domain binding remains a later adapter gate.

The first reviewed revision said it consumed a sealed summary but had no maturity
or sealed state. After one accepted bucket, it resolved immediately:

```text
observe(bucket=0, value=[70,70]) -> Ok
resolve_from_summary()           -> Ok(Resolved(1))       # first revision
```

The model was repaired during the review with a frozen three-bucket host horizon,
an explicit `seal_observations` transition, pre-maturity/unsealed refusals, and
post-maturity/post-seal observation refusal. The same one-bucket counterexample
now returns `Ok(Refused(NotMature))`. The seven-test suite covers these transitions.

**Remaining promotion gate:** a real Market must bind the exact
window/grid/expected range, source and evaluator versions, repair/failure policy,
and maturity rather than the host constant. Resolution must authenticate one
immutable `WindowResult` for exactly that domain. Retain early, late, and
truncated-prefix tests and add wrong-window, wrong-generation, reopened-result,
and repair-race fixtures.

The reference adapter initially retained a signer-only resolution placeholder,
which bypassed the repaired vertical authority. That final STOP was closed
during this review: `ExpectedBindings.resolver` was removed, and both
`Action::Resolve` and `Action::RedeemInternal` now unconditionally return
`ResolutionEvidenceUnavailable`. An arbitrary signed actor cannot resolve, and
even caller-supplied, internally coherent bytes forged into resolved lifecycle,
phase, and payout state cannot redeem. The 10 tests plus strict Clippy, rustdoc,
and fmt gates pass.

**Remaining promotion gate:** resolution and redemption may be reintroduced only
through typed evidence binding maturity, an immutable sealed WindowResult,
feed/source/evaluator versions, repair generation, exact Market terms, and
payout-set membership. The present refusal is correct but supplies no liveness
path.

### Repaired during review: reference materialization of an unaccounted claim

**Prior class:** P0 aggregate-supply authorization and external-asset
conservation. **Current single-position shadow result:** fixed and reproduced;
multi-position aggregation and real token movement remain explicit refusal
boundaries.

The first landed `programs/solana-reference` adapter reconstructed one
`Position` beside the market aggregate, but neither `validate_links`,
`validate_market_init`, nor `apply` checked that this position's active internal
plus external balances were reconciled with `KernelAccount.total_supply`. The
pure kernel intentionally delegates that reconciliation to its adapter.

An executed public-API counterexample supplied an otherwise canonical active
state with:

```text
position.internal[0] = 1
external.balances[0] = 0
kernel.total_supply[0] = 0
hoard.collateral_atoms = 0
```

The signed owner then requested `Materialize(outcome=0, quantity=1)`. The first
reference adapter revision returned success with:

```text
kernel.total_supply[0] = 0
external.balances[0] = 1
```

This was only an offline shadow, so no SPL token was minted. But it contradicted
the adapter's intended supply seam, and replacing the shadow with a mint CPI
would have materialized an unaccounted claim.

During the review, the adapter was explicitly frozen as a closed,
single-position model. It now requires checked equality
`position.internal[i] + external[i] == aggregate_supply[i]` before and after
every transition and requires zero hoard, internal, external, aggregate, and
replay state at initialization. The same counterexample now returns
`Err(AggregateClosureMismatch)` with no output. The new bounded trace test checks
quantities 1 through 16, and all 10 tests plus strict Clippy, rustdoc warnings,
and fmt pass.

**Remaining boundary:** this equality intentionally refuses multi-position
state; it is not an aggregate proof for a future account family. The eventual
program must authenticate canonical position/external PDAs, model the complete
set of positions or a committed aggregate update, and ensure every internal
issuance/destruction and SPL mint/burn path updates the one market aggregate
exactly once. No real token CPI or rollback property has been exercised.

The reference `KernelAccount.payouts` is also not cryptographically bound to
`MarketAccount.terms` or another immutable compiler artifact. This is a P1
immutability gap: initialization currently accepts any locally valid payout set
with the right outcome count.

## 3. Confirmed P1 semantic and arithmetic mismatches

### P1-A: fractional payout claims can be issued but may never redeem

The kernel deliberately refuses a redemption when
`quantity * weight / denominator` has a remainder. It nevertheless allows a
split of any positive quantity under such a payout set. For the checked fixture
`weights=[1,1], denominator=2`, splitting one atom and resolving makes each
one-unit claim individually unredeemable; the collateral remains trapped. This
is already demonstrated in the unit test as a refusal, but issuance does not
prevent the dead-end state.

This preserves solvency but fails exit liveness and the protocol requirement to
pay the frozen weight. Before admitting any non-one-hot payout vector, freeze and
implement either a redemption lot `D / gcd(weight_i,D)` enforced at issuance,
transfer, and redemption, or a persistent remainder-credit owner and terminal
residual rule. Until then, admit one-hot vectors only.

The static client's frozen fixture says
`exact-scaled-integer-floor-at-final-payout-boundary`, while the kernel refuses
instead of flooring. Even as an offline sample, the terms surface and executable
semantics give incompatible answers.

### P1-B: the landed batch crate is not the documented simplex relation

The crate clears one scalar grid tick for generic buy/sell quantities. Orders
carry no Market/Epoch/domain digest, outcome, portfolio coefficients, reserved
asset, cash amount, expiry, or price-scale/simplex vector. Candidates carry no
book/domain digest, score, fees, carry, virtual split/merge, per-asset closure,
page witnesses, or final settlement commitment.

It is a useful scalar batch-algorithm falsifier, but it cannot establish any
current claim about the documented coupled outcome distribution,
`BatchRelationV1`, portfolio limits, complete-set conversion, or collateral/Egg
conservation. Keep its evidence ledger separate from `P-BATCH-01..05` until a
language-neutral relation vector maps all those fields.

The vertical `BoundOrder` repair does not change that relation: clearing strips
the owner/outcome binding and passes only each scalar `Order` to `FixedBook`.
Consequently a buy bound to outcome 0 and a sell bound to outcome 1 can produce
positive matched volume, fee, and liveness charge even though every paired
settlement must refuse the outcome mismatch. Invalid owners/outcomes and
self-trade-only books are likewise not rejected at clear time. The frozen batch
relation must prove that its fills admit a complete executable pairing under
the bound asset/owner policy; checking bindings only during lazy settlement is
too late to make candidate volume economically meaningful. The executed minimal
fixture returned `matched=1`, charged one liveness unit, and then returned
`Err(InvalidFill)` for settlement.

### P1-C: the layout cannot reconstruct the kernel/protocol state

The fixed codec is locally strict, but the current account family has no
`SupplyLedger` containing internal and accounted external supply, no persisted
payout set/resolved payout index, no immutable window/maturity/repair policy, and
no liveness, Epoch, candidate, ClearWork, final-pot, or settlement-receipt state.
`MarketAccount.lifecycle` alone cannot reconstruct a resolved
`clutch_kernel::MarketState`; summing Position accounts is not an onchain option.

The later `programs/solana-reference` probe makes three of these omissions
explicit with reference-only Kernel, external-balance, and replay accounts. That
is useful architectural evidence and its 10 tests/full-byte vectors pass,
but its own documentation correctly refuses to freeze those layouts as the SVM
ABI. Its repaired single-position aggregate equality is a valuable refusal
boundary, not a multi-position state design.

Additional exact seams are unresolved:

- `RealmAccount` documents `max_outcomes` as “V1 must be 16,” but validation
  accepts any value in `2..=16`.
- `PositionAccount` accepts `reserved_cash_atoms > cash_atoms`; whether cash is
  total or free balance is not frozen.
- order pages enforce sorting only within one page. No current object proves
  cross-page order range, uniqueness, closure, generation, or frozen-page count.
- `OrderRecord.limit: u64` has no frozen mapping to the batch crate's
  `limit_tick: u8`.
- canonical IDs are hashes, not PDA/account-owner/upgrade checks. The docs state
  this correctly; an adapter must not confuse them.

Freeze one persisted-state ownership table before an adapter writes bytes. For
each kernel input and output, name exactly one authenticated account field and
one codec. Add encode/decode-to-kernel differential vectors, not just codec
round trips.

### P1-D: the accumulator's safe primitive is easy to compose unsafely

`Summary::twap`, `terminal`, extrema, and relative terminal/TWAP return values
remain available on gapped summaries. This is internally documented as
accepted-duration semantics, and the vertical model correctly gates gapped
resolution. A different caller can accidentally treat the result as a
full-window statistic because the statistic API itself does not bind a coverage
policy or expected range.

Window evaluation should take a registered policy plus exact expected range and
return a domain-bound result. Test that no partial prefix, gap-tolerant variant,
or accepted-only statistic can be substituted for a complete-window term. Keep
the generic accumulator source-neutral, but do not expose a bare summary digest
as settlement authority.

### P1-E: reference economics and vertical fees do not match consensus targets

- `research/economics.maximum_liability` accepts payout vectors whose weights
  sum to less than one; the Rust kernel requires equality. The two models do not
  enumerate the same admitted market set.
- the bounded categorical solvency walk covers one-hot payouts, not the kernel's
  fractional vectors or per-owner remainder liveness.
- vertical-model fees are created by incrementing `fee_revenue`; no payer cash is
  debited, no maker/executor/treasury allocation is performed, and the fee is
  `floor(matched * bps / 10_000)` on claim quantity rather than the documented
  simplex-dispersion/notional policy with persistent carry.
- consequently `fee_liveness_and_principal_boundaries_remain_disjoint` is a
  namespace check, not fee conservation or payer authorization evidence.

Keep the economics lab as hypothesis exploration, but require exact differential
fixtures against the eventually frozen fee and payout semantics before assigning
`P-SOLV-01` or `P-FEE-01` evidence.

### P1-F: cost goldens are not synchronized to the landed ABI

The cost lab clearly labels its layout values as hypotheses, but concrete codecs
now coexist with different values. Examples include a hypothetical fixed
Position size of `64 + 8*16 = 192` bytes versus the landed 220-byte Position, an
80-byte single-Egg record versus the landed 99-byte record, 4/8/10 KiB variable
pages versus the landed fixed 1,656-byte/16-record page (2026-08-19: now 1,819 bytes after page-set commitment fields, commit efb0ed5), and 32/128/512-order
batch cases versus the crate's `MAX_ORDERS=64`.

No cost conclusion should be attributed to the current layout or batch crate.
Generate an ABI inventory from the codec's single owner, retain the existing
hypothetical matrix as a separately named design arm, and add a differential
serializer before making packet/account/rent decisions.

### P1-G: collateral policy and account layout have unjoined profile identities

The collateral-profile lab is a useful independent policy model: its 19 tests
cover canonical 266-byte encoding, explicit collateral/fee/liveness currencies,
strict mint/account authority conditions, the pinned extension matrix, and
honestly offline DREGG assumptions. It is not yet enforced by the Rust layout or
reference adapter.

There are currently two different profile-digest algorithms:

```text
Python collateral policy:
  SHA-256("dragons-clutch/collateral-profile/v1" || 0x00 || policy_bytes)

Rust layout ProfileHash:
  SHA-256("dragons-clutch/profile/v1" || profile_bytes)
```

The reference adapter treats `ProfileAccount.profile` as an opaque
`ProfileHash`; its fixture hashes the unrelated bytes `fixture-profile`. It does
not decode the 266-byte policy, bind its digest as a subcomponent, authenticate
a mint or Hoard token-account snapshot, or enforce its extension/authority
refusals. This may become a deliberate parent-profile/subprofile construction,
but no byte owner or relationship is frozen today. Consequently an admitted
layout Profile does not currently imply admission by the collateral model.

Choose whether the collateral digest is the Realm's Profile ID or one
domain-separated field inside a broader Profile. Give that relationship one
canonical codec, cross-language golden vectors, and negative substitution tests.
Only a later SVM adapter may convert the offline mint/account snapshots into an
authenticated collateral-admission claim.

## 4. Formal-method and evidence gaps

These are confirmed gaps, not claims that the proposed proof approach is
unsound.

1. **Verus unavailable.** The toolchain lab correctly blocks E1. The batch
   shadow contains four `ensures true` placeholder proofs; these can verify
   vacuously and must never enter a theorem inventory. The kernel and accumulator
   shadows cover small algebra fragments, not executable refinement.
2. **Rocq unavailable.** `ClutchKernel.v` contains definitions and unproved
   `Prop`s only. Its final resolve clause is incorrectly shaped as
   `resolve s o = Some s -> ...`, requiring output equal input; active-to-resolved
   preservation is therefore effectively vacuous. Replace it with an `s'`
   output before proof work.
3. **No refinement relation.** There is no checked relation among Rust fixed
   arrays, the Rocq one-position list state, codec accounts, aggregate
   SupplyLedger, and adapter writes.
4. **No mutation/fuzz evidence.** Unit tests and deterministic models pass, but
   no property-directed mutation gate, malformed-byte fuzz corpus,
   cross-runtime vector manifest, SBF ELF, `program-test`, rollback, CPI, stack,
   heap, or total-CU evidence exists.
5. **Stage language has drifted.** `V1_BACKLOG.md` still checks “repository
   contains only pre-implementation specifications” while implementations now
   exist. `programs/README.md`, `crates/README.md`, the E0/E1 handoff, and the
   toolchain decision still say broad workspace/program work must wait for the
   Verus gate. The newer work can remain as quarantined probes, but milestone and
   evidence labels must be reconciled rather than implying stage completion.

## 5. Privacy, upgrade, and external-composition gates

### Privacy

The current order page is intentionally Clear: owner, order ID, outcome, side,
quantity, limit, minimum fill, flags, and generation are all public before any
batch relation is complete. There is no commit/reveal, encrypted mempool,
Shielded executor, Dark relation, timing-hiding, or transcript leakage budget.
That is not a defect for the transparent prototype, but it is a strict claim
boundary. Public placement/cancellation can leak participation and policy and
permit copy, cancellation, and censoring strategies. Any privacy mode needs a
separate versioned relation and threat model; it cannot be inferred from static
hosting or a hash commitment.

The static client duplicates `manifest.json` and `terms.json` data inside
`app.js`, and its smoke test does not compare the embedded objects/hard-coded
terms digest with those files. Drift can make the displayed binding differ from
the reviewed manifest. Also, a `frame-ancestors` directive in a meta CSP is not
an HTTP-header substitute; GitHub Pages hosting cannot be described as providing
that protection from this HTML alone. This matters before any wallet/signing
surface, not for the current disabled client.

### Upgrade and identity

No program data account, loader identity, upgrade authority, ELF digest, target
cluster feature set, Token-2022 deployment/profile, or source-program upgrade
policy is implemented. DREGG metadata is explicitly unchecked in the static
manifest, and the repaired top-level documents now preserve that same boundary.
Do not freeze its token program, decimals, extensions, or Realm eligibility
without an explicitly authorized authenticated inspection and a release-time
manifest.

The upgrade decision must also define what happens to active Markets if a source
program, token program, compiler preset, or Dragon adapter is upgraded. A stored
hash without an executable refusal path is provenance, not enforcement.

### External composition

The kernel returns mutated logical state, not the documented typed CPI intents.
Materialize/dematerialize therefore have no executable atomicity contract with a
future Token CPI. The adapter must preflight all logical arithmetic, authenticate
all account aliases/owners/mints, execute CPI, validate return and post-state,
and persist exactly the kernel transition under Solana rollback. Partial effects,
direct burns, extension-bearing Token-2022 accounts, transfer hooks, fees,
withheld amounts, close authority, delegates, and malicious program substitution
all need explicit refusal or accounting semantics.
